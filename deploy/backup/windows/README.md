# Windows backup encryption prototype

Preparation only. This module has not been independently approved, installed as
a scheduled backup, or used with application data. It does not create paired
database/media snapshots, transfer files, apply retention, deliver alerts, or
establish a successful application restore. Those are separate acceptance gates
in `BACKUP_IMPLEMENTATION_PLAN_20261107.md` at the workspace root.

The intended destination is the Windows project's `backups` directory. Recipient
keys belong in a separate `.backup-keys` directory, restricted to the Windows
owner and SYSTEM. Jenkins must not receive the private key. No production keys
have been generated by the prototype tests.

## Implementation

`SmokemapBackupCrypto.psm1` compiles the adjacent C# implementation using native
.NET cryptography. It requires PowerShell 7.4 or newer on Windows with NTFS ACL
support. No Git/OpenSSL installation or certificate-store changes are required.

Each file gets a random 256-bit AES key, wrapped for the recipient with
RSA-OAEP-SHA256. RSA keys must be 3072–8192 bits; the planned operational default
is 4096. Files use 1 MiB AES-GCM records, 16-byte authentication tags, an 8-byte
random nonce prefix and a big-endian 32-bit record counter. Every record
authenticates the complete header's SHA-256, its index and plaintext length.

The `SMKBKP01` header records format algorithms, chunk size, declared plaintext
length, bounded ASCII backup identity, recipient fingerprint, nonce prefix and
wrapped key. An authenticated empty final record and an exact EOF check reject
truncated files and appended records. Different files have independent content
keys. The format limits the data-record count to `uint.MaxValue`.

Verification requires an independently trusted backup identity, plaintext length
and SHA-256. Values copied solely from an untrusted envelope are insufficient.
Operational receipts must bind these values to the paired recovery manifest,
source/image identities and capture result, and remain protected on Windows.
The authoritative root receipt must retain the encrypted manifest's own
plaintext identity, length and SHA-256 outside that encrypted manifest. Restore
authenticates the manifest from those trusted root values before using its
entries to restore other files. Missing trusted root values fail closed.

Verification streams decrypted bytes into hashing without publishing plaintext.
Restore writes into a new private temporary file and publishes it atomically only
after every tag, final marker, declared identity/length and expected hash passes.
Existing destinations are never overwritten. Input streams use a no-follow
Windows file handle, and the module checks the ACL on the handle it reads.
Output operations keep the directory chain open without delete sharing until
publication or cleanup finishes. The output directory must have an owner/SYSTEM
ACL. The orchestrator must recover its interrupted temporary files before
starting a later operation.

## Validation already performed

The author ran `tests/Test-BackupCrypto.ps1` successfully: 45 checks covering
empty and chunk-boundary inputs, fragmented non-seekable streams, malformed
headers, corruption, truncation, trailing bytes, reordered records, wrong keys,
wrong identities/hashes, output collisions, ACLs, a dangling junction,
ancestor rename during publication, alternate data streams, and absence of
published plaintext after failure. The test process needs permission to create
a junction inside its disposable test directory. The suite uses disposable files
and test keys. Independent review is still required before operational use.

Do not generate operational keys or run this against application backups until
the independent source review and capture/transfer/restore plan pass. Never log
private-key bytes, raw database/media archives or application secrets.

## Paired export receiver

`Receive-SmokemapBackup.ps1` pulls an already completed export over the
noninteractive, host-key-verified SSH connection to Jenkins. The Jenkins owner
must publish `manifest.json`, `database.dump`, and `media.tar` under
`~/.local/state/smokemap-offvm-export/<run-id>/`. The manifest has
`schema: 1`, `run_id`, `environment`, and a `files` array in database/media
order. Each entry has `name`, `bytes`, and a lowercase SHA-256 `sha256`.
The publisher must expose the run only after writing the complete pair.

Supply existing owner/SYSTEM-only backup and receipt roots in separate
directories and the matching public and private recipient key paths. The
receiver checks file limits, lengths, and digests before encrypting and
verifying all three files. Readers require the separate root receipt, which
publishes last and holds the expected plaintext identity, length, and digest
of the encrypted manifest. If that final publication fails, preserve the
encrypted orphan for operator reconciliation. Run IDs are never overwritten.

`tests/Test-BackupReceiver.ps1 -RunId fixture-<12 hex digits>` uses disposable
Windows keys and directories. Prepare two synthetic Jenkins exports with
environment `fixture`: the named run with a valid manifest and the same run
with a `-bad` suffix and a deliberately incorrect media digest. The test
verifies transfer and decryption of the pair, corruption rejection, and
duplicate-run rejection. The receiver itself provides no capture scheduler,
retention, alerts, or application-level restore.
